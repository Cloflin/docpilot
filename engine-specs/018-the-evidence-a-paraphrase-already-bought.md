# 018 — The evidence a paraphrase already bought

> **Кратко.** `matchOpenerDense` находит, что вопрос — перефразированный опенер,
> и не может отдать ответ автора: язык не совпадает. До этой спеки находка на
> этом и заканчивалась — весь матч, включая найденную запись, откатывался в
> `null`, и ход шёл дальше на слабом сыром ретриве вопроса. Спека делает так,
> чтобы находка выживала: `matchOpenerDense` всегда возвращает матч, если он
> есть, `answer` в нём может быть `null` отдельно, и `session.ts` заряжает ход
> резолвнутыми чанками найденного опенера — тем же путём, каким follow-up
> наследует чанки прошлого хода (спека 013).

## Problem

**Матч находится и выбрасывается.** `openers.ts`, `matchOpenerDense`, последние
две строки до правки:

```js
const answer = answerFor(best, locale, uiLocale)
return answer ? { entry: best, matched: 'dense' as const, score: bestScore, answer } : null
```

`best` и `bestScore` уже посчитаны, порог `matchCos` и допуск `DENSE_MARGIN` уже
пройдены — а если `answerFor` отказывает (язык не тот), весь результат
схлопывается в `null`. Единственный вызывающий, `session.ts`, видел на этом месте
буквально ничего: ветка `if (dense) {...}` не срабатывала, и `queryVec` (сырой
эмбеддинг вопроса читателя) оставался единственной уликой, на которой строился
дальнейший ретрив.

**Измерено на боевом индексе этого пакета** (`3dc7547a`, 493 чанка,
`nvidia/nemotron-3-embed-1b:free`, `tau` 0.41):

| | значение |
|---|---|
| «С чего начать?» — L (лексика) | 0 |
| «С чего начать?» — D (сырой ретрив по 493 чанкам) | 0.28, z 0.152 — слабо |
| «С чего начать?» — G (итоговый вердикт) | 0.21 |
| «С чего начать?» — cosine к опенеру «How do I get started?» | **0.745** |
| второй по близости опенер | 0.058 |

Разрыв не косметический: 0.745 против сырого D 0.28 значит, что опенер-бейк уже
знает правильный ответ на этот вопрос — восемь якорей на страницы установки,
посчитанные один раз при индексации против настоящего корпуса — а сырой ретрив
вопроса «С чего начать?» находит их плохо, потому что короткая фраза на другом
языке эмбеддится ближе к короткому английскому вопросу, чем к длинной технической
прозе установочных страниц. Модель, которую всё равно вызовут (спека 019 снимает
гейт по умолчанию), получает на входе не ту улику.

## Research

**Почему не отдать ответ автора на другом языке.** Уже решено и протестировано:
`answerFor` (`openers.ts`) требует совпадения языка вопроса и языка bake, и тест
`'never serves an English answer to a Russian one'` держит это на лексическом
пути. Возврат матча без ответа — не обход этого правила, а его расширение на
второй сигнал: находка есть, текста для показа нет.

**Почему то же самое несогласованно уже существовало на лексическом пути.**
`matchOpener` (тот же файл) с самого начала возвращает объект вида
`{entry, matched, score, queryVec, answer}`, где `answer` может быть `null`
отдельно от остального результата — тест `'never serves an English answer to a
Russian one'` именно это и проверяет: `hit.answer === null`, `hit.matched ===
'exact'`. `matchOpenerDense` был единственным местом, где эта же ситуация
схлопывала весь результат, а не только текст. Приведение контракта к
единообразию — не новый паттерн, а починка расхождения.

**Почему `retrieval.fetch`, а не прямой `state.index.byId.get`.**
`seedFromHistory` (`harness.ts`) уже резолвит унаследованные чанки follow-up'а
именно через `retrieval.fetch` — ту же дверь, что `fetch_section`. Совпадение
пути означает совпадение гарантий: id, которого больше нет в индексе, тихо
отфильтровывается (`.filter(r => r.ok)`), а не падает. `matchOpenerDense` уже
требует `bundle.hash === index.manifest.hash`, так что `entry.ids` гарантированно
резолвятся против ЭТОГО индекса — гарантия сильнее, чем у `seedFromHistory`,
которая скрещивает ходы и переживает пересборку индекса между ними.

**Почему без нового потолка на количество id.** `SEED_FROM_HISTORY = 3`
(`harness.ts`) существует, потому что история разговора не ограничена и цепочка
наследования могла бы расти. `entry.ids` — противоположный случай: список,
посчитанный один раз при `docpilot index` фиксированным `k`, обычно 5–8 id,
авторский, а не читательский вход. Ограничивать нечего.

**Латентный баг, который вскрыла эта правка.** `session.ts` вызывал
`matchOpenerDense` при условии `!opener?.answer` — то есть даже когда лексический
проход уже НАШЁЛ опенер, просто без ответа. Раньше это было безопасно случайно:
`opener.queryVec` — это ровно вектор найденной записи, так что дальнейший
`matchOpenerDense` на том же векторе находил ту же запись (self-match, cosine
~1.0) и, с прежним контрактом, откатывался в `null`, если ответа не было — то
есть НИЧЕГО не делал. С новым контрактом self-match стал непустым результатом и
начал переписывать `turn.opener` с корректной провенанс `'exact'`/`'lexical'` на
`'dense'` — обнаружено тестом `'withholds the baked answer on a Russian page and
still skips the embedder'`, который упал сразу после первой правки. Условие
сужено до `!opener` (комментарий над ним уже говорил «runs after `matchOpener`
has DECLINED» — код теперь соответствует собственному комментарию).

## Decision

**`matchOpenerDense` (`openers.ts`) всегда возвращает найденный матч.**

```js
const answer = answerFor(best, locale, uiLocale)
return { entry: best, matched: 'dense' as const, score: bestScore, answer }
```

Тип результата: `null | {entry, matched: 'dense', score, answer}`, где `null`
по-прежнему значит «ничего не прошло порог», а `answer` внутри непустого
результата может быть `null` отдельно.

**`session.ts` заряжает ход эвидентом найденного опенера, если ответ не
отдаётся.**

```js
if (dense?.answer) {
  // подать ответ автора, как раньше
}
if (dense) {
  turn.opener = { matched: dense.matched, score: dense.score, baked: false }
  openerHint = dense.entry.ids
    .map((id) => retrieval.fetch(String(id || '')))
    .filter((r) => r.ok)
    .map((r) => r.section)
}
```

`retrieval = createRetrieval(...)` вынесен на одну позицию раньше — до блока
плотного матча, а не после него — потому что `retrieval.fetch` нужен здесь же.
Между старой и новой позицией ничего `retrieval` не читало, так что перенос не
меняет остального порядка.

**`harness.ts` мёржит `openerHint` туда же, куда `history`.**

```js
const inherited = seedFromHistory(retrieval, history)
const fromOpener = openerHint || []
const primed = [...gateResult.chunks]
const already = new Set(primed.map((c) => c.id))
for (const c of [...inherited, ...fromOpener]) {
  if (already.has(c.id)) continue
  already.add(c.id)
  primed.push(c)
}
for (const c of primed) emittedIds.add(c.id)
```

`openerHint?: any[]` добавлен в `RunTurnOptions` рядом с `history`.

**`gateResult`/`g` не трогается.** Соблазн — дописать `openerHint` прямо в
`gateResult.chunks`, раз `primed` и так начинается с него. Отклонено: `g` (`G`,
`D`, `L`, `channel`) — это то, что реально посчитал гейт, оно уходит в
`turn.gate` и оттуда в feedback-запись через `GATE_KEYS`. Вердикт 0.21 рядом со
списком чанков, заряженным на самом деле по 0.745, сделал бы будущее чтение этой
записи неверным необнаружимо. `g` описывает, что гейт посчитал; `openerHint` —
что ходу дали сверх этого; разницу называет только `turn.opener`.

**Провенанс становится наблюдаемым, не только у этой находки.** `turn.opener`
пишется в трёх местах и раньше не читался нигде — не в `GATE_KEYS`, не в
`slimTurn`, не в feedback-записи. Тот же пробел независимо найден у
`turn.notAnswerable` (пишется один раз, не читается нигде) при планировании
спеки 019 — оба чинятся одним проходом: `opener` и `notAnswerable` добавлены в
`StoredTurn`, в `slimTurn` (`history.ts`) и в объект, который строит
`writeFeedback` (`session.ts`), тем же принципом «маленькая фиксированная форма
без чанков — переживает архивацию целиком, как семь полей `gate`».

## Why it fits

Ничего нового по форме: `openerHint` — второй источник для того же `primed`,
которым уже пользуется `history`, резолвится той же функцией
(`retrieval.fetch`), той же дедупликацией. Ретрив (`retrieval.search`,
`fillResults`) не меняется вовсе — правка добавляет то, что модели ПОКАЗАНО
заранее, а не то, что ранжирует ретривер. `matchOpenerDense`'s собственный
комментарий («cannot change what a turn retrieves») остаётся верным в узком
смысле — про ранжирование; шире он теперь неточен и переписан.

## Cost and risk

**Цена — ноль дополнительных запросов.** Векторы уже посчитаны (опенер-бейк на
этапе индексации), резолв через `retrieval.fetch` — операция над уже загруженным
индексом в браузере читателя, без сети.

**Риск — self-match до правки условия.** Разобран в Research: без сужения
`!opener?.answer` → `!opener` лексический проход, не отдавший ответ, спровоцировал
бы избыточный, но безвредный по данным повторный проход плотного матча,
переписывающий `turn.opener` на `'dense'` вместо `'exact'`/`'lexical'` — неверная
провенанс, без изменения показанного читателю текста. Условие сужено, тест
`'withholds the baked answer on a Russian page and still skips the embedder'`
держит регрессию.

**Риск — заряженный эвидент без пользы.** Если сработавший опенер — не тот,
который на самом деле нужен читателю (тай-брейк `DENSE_MARGIN` уже отсекает
близкие ничьи, но не гарантирует смысловое совпадение), модель получает лишние
чанки в контексте. Цена — токены промпта, не корректность: модель по-прежнему
обязана цитировать реально показанное (`emittedIds`), а лишний неиспользованный
чанк ничего не портит, только не помогает.

## Checks

- `test/openers.test.js`: новые кейсы — `matchOpenerDense` возвращает
  `{entry, matched: 'dense', score, answer: null}`, а не `null`, при сильном
  cosine-матче и несовпадении языка; тот же контракт для записи без bake-ответа
  вообще (существующий тест переписан под новую форму).
- `test/docpilot.test.js`, `describe('runTurn — a follow-up inherits what the
  last turn cited', ...)`: новые кейсы для `openerHint` — чанк доходит до
  промпта и до `emitted`; дедуп не даёт того же чанка, что уже нашёл гейт,
  появиться дважды (сравнение счётчиков, а не абсолютное число вхождений); ход
  без `openerHint` побайтово совпадает с ходом, где `openerHint: []`.
- `it('drops the reasoning, the retrieved chunks and everything transient', ...)`
  (`history.ts`'s `slimTurn`): `opener` и `notAnswerable` теперь в списке
  переживающих архивацию ключей, с проверкой формы.

## What this does not do

**Не меняет, что показывает `retrieval.search`.** Ранжирование строк результата
(`fillResults`) и то, что видит `search_docs` при повторном поиске моделью —
из этой правки не следует ничего; `openerHint` — только предзагруженный
контекст, посчитанный один раз до входа в цикл харнеса.

**Не решает вопрос без совпадения с опенером.** Вопрос, не похожий по смыслу ни
на один из трёх–пяти сконфигурированных опенеров, этой правкой не выигрывает
ничего — для него по-прежнему единственный сигнал это сырой `queryVec`, и именно
поэтому нужна спека 019: без неё гейт откажет такому вопросу до модели, чем бы
он ни был заряжен.

**Не трогает `matchOpener`'s (лексический) контракт.** Он уже возвращал матч с
`answer: null` — эта спека приводит плотный проход к тому же виду, а не меняет
существующий.
