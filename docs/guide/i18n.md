# Translating the panel

Every reader-facing string is replaceable, one string at a time.

## The shape

```js
docPilot = {
  i18n: {
    // Applies to every locale.
    translations: {
      empty: { heading: 'How can I help?' },
    },
    // Keyed by VitePress locale.
    locales: {
      ru: {
        translations: {
          empty: { heading: 'Чем помочь?' },
          composer: { placeholderNoProduct: 'Спросите про документацию' },
        },
      },
    },
  },
}
```

The inside is byte-for-byte VitePress's own [local-search i18n](https://vitepress.dev/reference/default-theme-search#local-search-i18n), so their example transfers here unchanged. The outer key is `i18n` rather than `locales` because a VitePress config already has a top-level `locales` meaning something else, and two keys with one name in one file is a support question waiting to happen.

**Overriding one string keeps the other hundred.** The merge is per leaf, never per block.

## Two selectors, one key space

There are two different "reader's language" in this panel, and conflating them regresses behaviour that already ships.

| | driven by | covers |
|---|---|---|
| **UI locale** | the page's locale (`lang`) | every button, label, aria name, status line and refusal |
| **Reply locale** | the language the reader **typed** | `reply.credential.*` and `reply.social.*` — the two copies the host writes with no model call |

Which selector a key uses is a property of the key and is not configurable: everything under `reply.` follows the typed language, everything else follows the page.

One selector for both would have to pick a regression: either a Russian greeting answered in English, or Russian written into an English page's chrome. Both were behaviours that worked before the i18n layer existed, and neither is worth trading.

Both selectors are **subtags**, which is the point. A site that already declares `locales: { ru: … }` in VitePress writes one `ru` block here and covers its chrome *and* its replies.

## Fallback, per leaf

1. `i18n.locales[selector].translations.<path>`
2. `i18n.translations.<path>`
3. for `reply.*` only: `i18n.locales[<page locale>].translations.<path>` — a reader typing an unrecognised language on a Russian site is better served Russian than English
4. the shipped default for that locale
5. the shipped default for `en`

A regional tag is normalised to its subtag: `ru-RU` finds `ru`, `en-US` finds `en`. A locale nobody ships and nobody configured falls back to English rather than rendering blank.

A key that does not exist is **dropped and named on stdout**:

```
[docpilot] i18n.translations.empty.headng is not a key this panel has — dropped
[docpilot] i18n   root + 1 locale (ru) · 1 unknown key ignored
```

Failing a docs build over a typo in copy would be out of proportion — but so would swallowing it, which is why the drop is loud.

## Interpolation

`{name}` for a value, `{n, singular|plural}` for a two-form plural:

```js
refusal: {
  searchedAndRead: 'Searched {scope} and read {n} {n, page|pages}',
}
```

Two forms only, deliberately. This is a UI string table, not an ICU runtime, and the four strings that count anything count pages or sources. A language whose plural rules need more than two forms overrides the whole sentence — which is what the override mechanism is for.

## What is not translatable

**The system instruction.** `promptHash` names every eval report, and `eval` refuses to diff two reports built from different instructions. A translatable prompt would give two readers of the same build two different hashes and break every cross-report comparison there is.

Change the instruction with `prompt.override` / `prompt.extend`, which are build-time and singular, and remember that `languageDirective` already makes the model answer in the reader's language — a translated system prompt buys nothing and costs the hash.

The prompt disclosure's **headings** are chrome and are in the table (`promptDoc.heading*`). Its **bodies** are the exact bytes sent to the model; translating those would make the disclosure a description of something other than what was sent.

**Page and section titles.** The scope picker shows corpus text. Translating a page title would name a page that does not exist.

## Finding the answer, before there is one to translate

The panel answers in the reader's language whenever it answers at all — but a
question has to reach the model first, and that is a **retrieval** problem
rather than a translation one.

A dense channel handles it: the question is embedded verbatim, no translation
step anywhere, and a multilingual embedder puts a Russian question and an English
paragraph near each other by meaning. **A lexical channel cannot.** BM25 matches
words, and a Russian question shares no word with an English corpus — so on a
site with no embedder ([`embed: false`](/reference/config#embed-false), an
embedder that stopped answering, an index built with another model) the score is
zero, for a question the corpus answers perfectly well.

Two things close that, and neither is `i18n`:

- **[`vocabulary`](/reference/config#vocabulary)** declares the words readers use
  for what your documentation calls something — including in their language.
  `npx docpilot vocabulary` proposes the map; the rewrite runs over the index and
  the query through one tokenizer, so both sides meet on the same token.
- **[`guard.mode: 'dense-only'`](/reference/config#guard-mode-guard-supportminidentifiers)**,
  which ships, stops a verdict computed from lexical coverage alone from ending
  the turn. The words a map does not carry are exactly the ones nobody thought to
  declare, so the model — which is shown the passages and can read them — decides
  instead.

**A follow-up has a third thing behind it.** *«а я могу его стилизировать?»*
retrieves nothing on its own in any language — the pronoun is the question — so
the gate also scores it composed with the previous question. The check that
keeps that composition honest asks whether a word of the follow-up appears in
the retrieved evidence, which no Russian word can do over an English corpus, so
it stands aside for a tail whose words and letters are both foreign to the
corpus and lets the dense channel decide. Same script, different language —
French over English docs — is `vocabulary`'s job, as above. See [The refusal
gate](/concepts/the-gate#follow-ups).

The refusal copy itself follows the **page's** locale rather than the language
the question was typed in, like the rest of the panel chrome; only `reply.*`
follows the reader. That is the split [Two selectors, one key
space](#two-selectors-one-key-space) describes.

## One thing this cannot check

`themeDocPilot` validates key *paths*, but it does not see VitePress's own `locales` — so an override for a language your site does not publish validates cleanly and never renders. If a block appears to do nothing, check that the locale key matches one your site actually has.

## Where the merge happens

Validation is in Node, at build time. The **merge** is in the browser.

`themeConfig` is inlined into the hydration payload of every page, so merging server-side would ship the whole default tree — a hundred UI strings plus eighteen languages of reply copy — on every page of the site. Only your delta crosses; the defaults stay inside the panel's own lazily loaded chunk, where they already were.
