# DocPilot 2.0 — documentation structure research

> **Кратко.** Главный вывод: первым делом читатель должен выбрать между STATIC и SERVER, поэтому эта страница выбора идёт сразу после введения. Людей убеждают измеренные числа (точность, отказы, атаки, задержка, байты), а не прилагательные: разработчики всё меньше доверяют ИИ (по Stack Overflow 2025 около 46% не доверяют точности), поэтому доказательства и ссылки на источники — главный товар. Для ИИ-агентов продаётся llms.txt, markdown-зеркала и MCP; у Mintlify и Kapa это уже стандарт. Структура сайта строится по Diátaxis (tutorial / how-to / reference / explanation), а «Измерять и улучшать» и «Безопасность» становятся отдельными разделами верхнего уровня. Старые разделы Guide и Features разбираются по типам, а функции остаются исчерпывающе описанными на своих страницах. Сначала переписать: Introduction, выбор установки, Quick start (два пути), Measure and improve, Security, Server runtime.

## 2. What matters to people (evidence-backed)

| Finding | Evidence | Consequence for DocPilot docs |
|---|---|---|
| Missing or outdated docs are the top obstacle to using an API | Postman State of the API: lack of documentation ranked first in 2020 (54.3%), 2021 (~55%), 2022 (a majority); outdated docs cited as top concern in 2023 | Every feature has its own complete page; a docs page that goes stale is a defect. The refresh gate (corpus hash test) is a selling point. |
| Developers use AI more and trust it less | Stack Overflow 2025 (secondary coverage): ~84% use or plan to use AI; ~46% distrust accuracy (up from 31%); trust figures reported as 29–33%; 66% name "almost right, but not quite" as the top problem | Lead with verifiable accuracy, not "AI-powered". Show how a wrong answer is prevented or caught. |
| Fluent answers hide weak citations | Stanford (Liu et al.): about half of generated statements lack supporting citations and only ~75% of citations support their claim, across four generative search engines; fluency correlated inversely with citation quality | Citations alone are not proof. Publish citation precision/recall from the eval suite. |
| Few readers check sources | Secondary reports (Pew via an arXiv preprint): click on a cited source in ~1% of visits | Sources must be one click away and show the exact passage (existing feature). The measured metric matters more than the reader's checking. |
| Docs must be scannable, task-first, accessible | Google style guide: conditions before instructions, descriptive link text, sentence-case headings, numbered lists for sequences. Fluent 2: start from the audience; plain scannable language; descriptive links; no directional words ("above") | Section 6 checklist. |
| Content gaps, not the model, cause bad answers | GitBook AI docs: hallucination is treated as a content gap; write explicit content | Supports the `improve` loop: failures on a golden set become corpus edits. |

Limit of this evidence: no source found that measures trust in documentation chat specifically. Treat the above as adjacent evidence; DocPilot's own eval numbers are the primary proof.

Claims for AI agents (the same product, a different reader):
- Docs consumable by agents: `llms.txt` with descriptions, markdown mirrors of every page, structured reference (config and CLI as tables, JSON schemas), stable URLs. Proof: a check that every page has a markdown mirror and an llms.txt entry (a CI gate).
- A machine entry point: MCP server or `/.well-known` discovery is where Mintlify and Kapa position (Kapa: hosted MCP and a retrieval API). If DocPilot ships one, document it; if not, do not imply it.
- The Claude Code agent that tunes a site: proof is the metric delta it produced and the token cost per task (model and effort chosen per task).

Rules for the proof: print each number once at its source and link to it (the repo already has a gate for printed figures; keep using `scripts/refresh-figures.mjs`). Never publish a number without split, sample size and the rerun command. No vendor-style "99% accurate" without a method.

## 5. Page templates

**Install-choice page (`/install/choose`)**
1. One-sentence answer: "Use STATIC if X. Use SERVER if Y."
2. Decision table, 6 rows: corpus private?, prompt private?, rate limits needed?, bytes to reader, TTFT, setup time, hosting needed.
3. Diagram of both data flows (what leaves the browser/server).
4. Measured numbers with link to source and rerun command.
5. Two buttons: "Start with static" / "Start with server".
6. What you can change later (migration path).

**Feature page (F)** — exhaustive on its own page
1. What it does, one sentence + a screenshot or 10-second clip.
2. Availability: STATIC / SERVER / both; since version.
3. How to use (reader's view).
4. Configuration: every option, default, allowed values, example (table).
5. Behaviour details and edge cases (all of them, here — not on overview pages).
6. Limits and failure modes; what the reader sees.
7. Security and privacy note (what data goes where).
8. Related features, CLI commands, and metrics affected.

**How-to (H)**
1. Title: verb + object. Goal in one sentence.
2. Before you start (prerequisites, versions, time).
3. Numbered steps, one action each; condition before action.
4. Expected result (output/screenshot).
5. If it does not work (3 most common errors).
6. Next steps (links with descriptive text).

**Tutorial (T)**
1. What you will build, time, what you need.
2. Steps with a visible result after each.
3. The finished result and what to try next. No option lists, no theory.

**Reference (R)**
1. One-line purpose.
2. Table or list mirroring the thing's structure (CLI flags, config keys, endpoints, metrics).
3. Per entry: name, type, default, effect, example.
4. No tutorial prose; link to the how-to and concept instead.

**Concept (E)**
1. The idea in 3 sentences; diagram first.
2. Why it works this way; trade-offs and alternatives rejected.
3. How it connects to other parts.
4. Links to the how-tos that use it.

**Overview/landing (L)**
1. The one thing this section is for.
2. A short list of what is here, ordered by what readers need first.
3. Only the main path; no option detail.

## 6. Writing rules — checklist

Structure
- [ ] Important information first: the answer or the action is in the first sentence; conditions before instructions (Google).
- [ ] One Diátaxis type per page. Test with the two questions: does the page tell the reader what to do or what to know; is the reader studying or working.
- [ ] Overview pages hold only what matters; every detail lives once, on its own feature or reference page, and is linked.
- [ ] Every feature page covers: config options, defaults, edge cases, limits, security note, availability (STATIC/SERVER).
- [ ] Every number is printed once at its source and cites the split, sample size and rerun command.
- [ ] No announcements of future features (Google). Use "Added in 2.0" markers only for released behaviour.

Words (Material/Fluent/Google/Microsoft common core)
- [ ] Address the reader as "you"; active voice; present tense; short sentences.
- [ ] Sentence case for headings, buttons and labels; no end punctuation in headings and buttons; no exclamation marks.
- [ ] One term per concept (use the glossary: "gate", "golden set", "dev split", "test split", "STATIC", "SERVER"); no synonyms.
- [ ] Link text names the destination ("Read the eval report reference"); never "click here" or a bare "Learn more"; no "above/below".
- [ ] Verb-first buttons and CLI task names; imperative steps; one action per step; numbered lists for sequences.
- [ ] Errors tell how to fix, next to where they occur ("Set `server.timeoutMs` below 30000"), no blame, no "oops".
- [ ] Empty states and "no result" docs states point forward: what to run next.
- [ ] UI elements in bold, code in code font, descriptive alt text on every image and diagram; do not rely on colour alone.
- [ ] Plain words, no idioms; strings that appear in the UI stay translatable (no concatenation).
- [ ] Standard American spelling, serial commas, unambiguous dates.

Agents
- [ ] Every page has a markdown mirror and an llms.txt entry with a description that says what the page answers.
- [ ] Reference pages use tables and stable headings so a model can quote them.
- [ ] No page depends on a screenshot alone: state the content in text.

Process
- [ ] Edit docs, then reindex, then refresh figures, then reindex (repo gotcha: two rebuilds, paid); batch all doc changes into one pass.
- [ ] Docs changes that move a page add a redirect.
